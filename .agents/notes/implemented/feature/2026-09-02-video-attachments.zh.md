# Agent Note: 持久视频附件

Status: implemented

[English](2026-09-02-video-attachments.md) | 中文

## 问题

Web 会话契约已经包含视频接收和渲染引用，但附件存储、模型适配器、Host 准入和受权读取仍只支持图片。这个不完整能力会阻止干净构建，也无法持久重建包含视频的模型请求。

## 决策

视频是第二种持久附件类型，拥有独立的媒体类型、字节和数量限制、内容引用、本地容器校验和验证读取路径。Host 解码规范 base64，在追加所属用户消息前保存每个视频，只为该会话中引用的附件授权读取，并在准入或切换模型前拒绝不支持视频的模型。

客户端继续在现有输入归属中保存未发送的视频文件和对象 URL。ui-conversation 声明视频消息 Slot，ui-attachment 渲染附件栏、历史视频控件和混合媒体灯箱。LLM 内容映射携带 VideoBlock；适配器要么显式序列化该类型，要么拒绝它。直接 DeepSeek 适配器保持不支持视频。

## Alternatives considered

**移除不完整的视频 UI。** 这会通过删除已有的多模态契约、MIME 接收和展示工作来使构建通过。完整的持久附件路径保留产品能力。

**将视频视作图片。** 视频容器具有不同的校验方式，不使用图片归一化或路由专属图片请求策略，模型也可能只支持其中一种模态。带标签的附件类型使每个消费者明确自己的行为。

## Consequences

视频准入复用图片路径的持久化顺序和受权会话读取，但保持独立的限制和容器检查。提供方能力是显式的：视频只会到达声明支持它的路由，而没有视频历史的会话仍可使用仅图片和仅文本路由。
